Agent 评测（Evaluation）

文档状态：已实现（2026-11-13）。 本章描述 crates/eval 提供的评测能力：用例格式、两个 runner、 判分器、报告与可比性。它是一套验证工具，不是产品运行时的一部分。

评测要回答一个问题：某次改动让 Agent 变好了还是变坏了。回答问题需要三样东西同时成立： 用例可重复、证据来自运行本身而不是模型自述、两次运行的数字可比。 Tact 的既有结构让这三件事都不显然，本章先解释约束，再给出形状。

1. 为什么需要一个独立 crate

评测代码依赖产品：它要启动会话、跑真实内核、读真实用量。 产品不依赖评测。这条方向由 scripts/check-packaging.py 强制：任何其他 crate 依赖 tact_eval，构建即失败。

这条围栏的作用不是洁癖。如果评测挂在 tact-ui 里， suite runner、判分器和报告格式就会随产品二进制一起发布， 变成 semver 表面的一部分，也会把评测专用依赖拖进每一次产品构建。

位置 内容
crates/eval/src/case.rs 用例与判分器声明，TOML 解析与校验
crates/eval/src/suite.rs 加载目录、解析 fixture、准备每次尝试的工作目录
crates/eval/src/runner.rs RunArtifact、RunIdentity、Runner trait
crates/eval/src/host_runner.rs 进程内运行，拿得到类型化停止原因
crates/eval/src/cli_runner.rs 子进程运行 tact-ui headless
crates/eval/src/process.rs 子进程的统一生命周期：超时、进程组、有界读取
crates/eval/src/grader.rs 三种判分器与 verdict 折叠
crates/eval/src/report.rs 报告、汇总、指纹、schema 版本
crates/eval/src/options.rs 一次运行的配置，两个 runner 共用

2. 三条来自既有实现的约束

AgentUpdate 不可序列化，且丢掉结果

tact_protocol::AgentUpdate 只有 Debug 和 Clone；它的 RunFinished { run_id } 不带 outcome。 tact::AgentLoopStop 是为进程内 Goal Runner 设计的， 刻意不带 serde。于是停止原因、轮次数、工具调用数只在跑它的进程活着时存在。

这直接决定了 RunArtifact::stop 和 turns 是 Option 而不是带默认值的枚举。看不见的 runner 说 None，报告渲染成 unknown；写成 0 会让一个猜测混进套件的平均值。

配置是进程全局的

tact::config::install 每次进程只装一次。 模型、endpoint、权限模式因此属于一次运行，不属于单个用例。 用例文件里写 model 会是个进程内 runner 无法兑现的旋钮， 而撒谎的旋钮比没有旋钮更糟。

推论是并行的位置在上一层：run_suite 顺序执行， 需要不同配置的调用方启动多个 tact-eval 进程。

headless 无法回答权限提示

tact-ui headless 只能跑在 auto 或 plan。默认权限模式是 Default（每次询问）， headless 会把每个需要工具的用例都判成失败。因此 RunOptions 的默认是 Auto，且这处偏离只写在一个 impl Default 里。

3. 用例

用例是可版本化的数据，每个用例一个 *.toml。

prompt = "Create hello.txt containing exactly: hello eval"
timeout_secs = 180

[isolation]
kind = "copy"          # 或 "empty"
fixture = "fixtures/seed"

[[graders]]
kind = "files"
name = "hello-file"

[[graders.assertions]]
kind = "contains"
path = "hello.txt"
text = "hello eval"
字段 含义
id 缺省取文件名，套件内必须唯一
prompt 用户会给 Agent 的那句话
timeout_secs 整次尝试的墙钟预算，默认 300
isolation empty 或 copy { fixture }
graders 决定用例成败的判分器列表

EvalCase 用 deny_unknown_fields。 把 timeout_secs 拼成 timeout_sec 会让加载失败， 而不是悄悄退回默认值——一个本想限制慢用例的预算，若静默失效， 判分就会按错误的预算进行。

校验分两层。EvalCase::load 只判断文件本身能决定的事： prompt 非空、超时为正、判分器合法、正则能编译。 fixture 是否存在要等 EvalSuite::load， 因为相对路径只有相对套件目录才有意义。

正则错误在加载期拒绝，而不是判分期。否则它会以 Fail 的形式出现，读起来像"Agent 没做到"， 而真相是"用例提了一个不可能的问题"。

4. 判分器

判分器只读两样东西：runner 产出的 RunArtifact， 和运行留下的工作目录。它不知道是哪个 runner 跑的， 也从不询问模型"你觉得自己做完了吗"。

kind 判定
command 在用例目录执行 shell 命令，退出码 0 通过
files exists、absent、contains、matches
answer contains、not_contains、matches、non_empty

Verdict 是三态

enum Verdict {
    Pass,
    Fail { reason: String },
    Inconclusive { reason: String },
}

三态不是过度设计。把"无法判断"并入"失败"， 一次坏掉的 harness 就会变成一次假回归； 并入"通过"，一个没测到的用例就会伪装成绿灯。

折叠规则按优先级排列，写在 CaseOutcome::verdict：

  1. 记录了 RunFailure（超时、启动失败、harness 错误）→ Inconclusive。harness 的问题不计入模型成绩。
  2. 运行是 EmptyTurn 且用例没有 answer 判分器 → Inconclusive。文件判分器可能通过，但没有任何证据表明请求被回答了。
  3. 任一判分器 Fail → Fail，并带上判分器名。
  4. 任一判分器 Inconclusive → Inconclusive。
  5. 否则 Pass。

没有判分器的用例同样判 Inconclusive，不是通过。

5. 两个 runner

HostRunner（进程内）

直接调用 bootstrap_session 与 agent_loop_detailed，与 TUI、headless 用同一套启动路径。 它唯一能拿到的东西是 AgentLoopOutcome： 真实停止原因、轮次数、工具调用数。这是它存在的理由。

它刻意不走 tact_host::HostSession。后者把一轮对话暴露成 UserCommand::SubmitTask 加 HostEvent::Agent(AgentUpdate)，而 AgentUpdate 不带 outcome，走它就等于把类型化的停止原因换成从日志里猜。

代价是配置进程全局，一次运行的用例共享同一个模型和权限模式。 这也是 run_suite 顺序执行的原因。

CliRunner（子进程）

启动 tact-ui headless，读它写入的三样东西： stdout 上的最终答案、stderr 上的每行一个事件、退出码。 它能对 release 二进制或容器工作，这正是 CI 需要的形状。

它读不到的字段留 None：缓存命中 token、推理 token、 工具参数摘要。日志行里没有这些字段，所以是 unknown，不是 0。

两边的证据必须同名同义

两个 runner 产出同一个 RunArtifact， 过同一批判分器，因此同一套件在两条路径上得分方式一致。 两处刻意的差异都在类型上可见：

struct ToolRecord {
    name: Option<String>,      // 日志行没点名工具时是 None
    args: Option<String>,
    message: Option<String>,
    status: ToolStatus,
    duration_ms: Option<u64>,
}

struct TokenTotals {
    prompt: u64,
    completion: u64,
    cache_hit: Option<u64>,    // CLI 路径看不到
    reasoning: Option<u64>,
}

CLI 日志里 [tool failed] 有两种来源：完成步骤 （[tool failed] {tool} {message} (Nms)）与 provider 活动失败（[tool failed] {error}，不点名任何工具）。 把后者当成前者，就会把一句错误信息读成工具名。 所以只有行本身能证明时才归因，否则 name 为 None、文本进 message。

6. 超时与进程

评测里最容易出错的不是判分，是"什么时候该停"。

超时的运行不能被判为通过

到预算时 HostRunner 调用协作取消，而 agent loop 会返回 RunStop::Cancelled。如果只按 loop 的返回值分类， 一次"先写好文件、再卡住"的运行会拿文件判分器判定通过。 所以 runner 记住预算是否耗尽，无论 loop 怎么返回都记为 RunFailure::Timeout，让这次尝试落在 Inconclusive。

进程组与它够不到的地方

process::run_child 让子进程自成一个进程组， 超时对整组发信号。这能收掉留在组里的孙进程。

但 Tact 自己的 bash 工具和 background_run 会把它们的子进程放进新的进程组， 超时时仍在运行的工具有可能不在被杀的组里。模块文档直说这条边界， 不假装覆盖。要覆盖需要按平台枚举后代进程，那是另一个改动。

读取必须有界

子进程正常退出，但孙进程（cmd &）仍持有 stdout 时， 管道不会关闭。无界的读取会一直等到孙进程结束—— 对判分器来说，一个开发服务器就能让整个套件挂死。 现在等待有上限，输出在读到时即写入共享缓冲， 所以截断也不会把已到的内容一起丢掉。

7. 隔离与成本

每次尝试在自己的目录里跑：$TMPDIR/tact-eval/<case>/<uuid>。 相对 fixture 在 EvalSuite::load 时相对套件目录解析并校验； 之后判分只读这个目录，与进程 cwd 无关。

判分后目录被删除。一次运行会留下整棵源码树和一个 SQLite 会话， 任何规模的套件都会把磁盘填满。删除也解释了为什么报告里的 session_id 是标签而不是句柄：它指向的 .tact/tact.db 在读者看到 JSON 时已经不存在。

每次尝试有自己的 .tact/tact.db 和 session id， 所以会话锁与数据库都不共享。这是并行安全的结构性保证， 而不是靠加锁。

8. 报告与可比性

报告是 stderr 上的一张表加 stdout 上的 JSON。 JSON 带 schema_version，因为报告由一个版本写出、 由另一个版本读取（CI 产物、外部平台摄入），读者需要一个数字来判断兼容性。

下面是 suites/smoke 用 CLI runner 跑两次的真实输出：

runner=cli model=unset endpoint=unset mode=auto attempts=2
suite=9549eddcaa2ae102

answer-only                      pass 2/2 (100%), fail 0, unknown 0
write-a-file                     pass 2/2 (100%), fail 0, unknown 0

cases passing any attempt: 2/2
cases passing every attempt: 2/2

model 与 endpoint 为 unset 是因为这次运行没有传模型参数，而不是配置为空： runner 不知道它跑的模型，于是如实说不知道。

指标 含义
cases passing any attempt pass@k，k 为 --attempts，适合噪声大的模型
cases passing every attempt 严格口径，回归门禁用这个
pass_rate 忽略 inconclusive 尝试；全无决定性尝试时为 n/a，不是 0

ReportMeta 记录 runner、身份（模型、endpoint、权限模式）、 尝试次数，以及整个用例集的指纹。指纹哈希用例的书写形式—— prompt、超时、隔离、判分器——所以改了判分器或超时都会改变指纹， 不能把两个不同套件的结果放在一起比较。 它特意在 fixture 解析为绝对路径之前取值， 使同一套件在任何工作目录下指纹一致。

identity.model 为 null 表示 runner 看不到， 典型情况是完全由 --config 驱动的 CLI 运行。 两个都为 null 的运行并不因此可比，配置要自己核对。

9. 命令行

# 不需要模型、二进制或 API key 的部分，适合每个 PR 跑
tact-eval validate suites/smoke

# 跑一次套件
tact-eval run suites/smoke \
  --runner host --attempts 3 \
  --provider deepseek --model deepseek-v4-pro

# 黑盒路径，对着已安装的二进制
tact-eval run suites/smoke --runner cli --binary ./target/release/tact-ui

# 回归门禁
tact-eval run suites/smoke --strict --json-out target/eval/report.json

--strict 只在每个用例的每次尝试都通过时退出 0。 一次失败或一次 inconclusive 都会让整个运行失败， 所以它适合小而精的套件，不适合测噪声大的模型。

相对 --config 与 --binary 都会在构造时规范化为绝对路径， 因为每次尝试都在用例自己的目录里启动子进程。

10. 不是密闭的

一次尝试会继承操作者的 $HOME： ~/.tact/config.toml、hooks.json、用户 skill、 插件缓存、按仓库划分的 memory 目录都会影响运行。 --config 只固定模型配置，别的都不固定。

需要密闭的套件应把 HOME 指向临时目录：

HOME=$(mktemp -d) tact-eval run suites/smoke --runner cli ...

这条在文档里说明而不在 harness 里强制，因为强制会破坏 开发者在本机跑自己的套件这个常见场景。

11. 当前限制

限制 原因 下一步
CLI 路径没有类型化停止原因 日志没有该字段 给 headless 加 --events ndjson，写 AgentEvent
CLI 路径的 stderr 语法是手抄的 格式定义在 headless_log.rs 把 format_event/parse_line 移到 tact_protocol
缓存/推理 token 在 CLI 路径为 None 日志行无字段 同上
进程组杀不到 bash/background_run 的子进程 它们各建新进程组 按平台枚举后代，或 Linux PID namespace
运行结束后工作目录已删 磁盘成本 --keep-work-dir 用于复查
无 LLM 评委判分器 评委需要先对着已知判定的套件校准 有了稳定套件之后再加
用例不并行 配置进程全局 由调用方启动多个进程
