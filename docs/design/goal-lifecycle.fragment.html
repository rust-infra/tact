Goal 生命周期状态
draft → queued → running → verifying → succeeded
draft → queued：验收标准仍在确认，尚未授权 Runner。/goal create 不写 -- 段时没有标准，Goal 走「模型提交完成提议即完成」并标注 self-attested；写了才把每条片段变成必需的人工标准，完成前需 /goal accept。自动验证尚未实现，Automatic 标准仍被拒绝。
Run：一次执行权 = 一到多个受限 activation
activation 1 → activation 2 → activation 3 → … activation N
下一周期只在「上一个 activation 有可观察进展（跑过工具调用或追加过 Goal 事件） 且预算仍有剩余」时才启动；纯文字回合结束本次 Run。
累计预算（同一条 Run 记录） 500 turns · 600s 墙钟 · 跨 activation 累加
queued → running：driver 创建后立即把 Goal 交给 Runner，不需要额外启动命令。 Runner 取得 lease、创建一次有预算的 Run，Agent 检查现状、规划并维护关联 Task DAG。 该 activation 跑在命令循环之外的可取消任务里，所以运行期间 /goal list / pause / steer / cancel 仍然可响应。
每个周期重建注入上下文：Runner 重新读 Goal、关联 Tasks 与事件事实，把 <goal-context>（目标 / 标准 / Tasks / 最近 checkpoint / 暂停原因） 注入 activation。它是派生产物，不是用户消息：MessageKind::GoalContext 与标记双重标识，compaction 重建不把它当作用户回合保留，TUI 历史不渲染它、 也不计入 ⟳ —— 面板才是它的权威视图。
每一轮传的是「剩余」额度：交给 agent loop 的是 max_turns - turns_used，且上限在 turns_taken 自增之前检查 —— 所以停下时那次探测不会被记成一次模型调用，多 cycle 的 Run 不会花到约 2× 预算。 工具调用数只作用量记录（tool_calls_used），不设单独上限：每次工具调用 本就发生在一次模型调用之内，turn 上限已经约束了总扇出。
checkpoint：每次 activation 常驻
每次注入的 <goal-context> 都带 <checkpoint-protocol>； turn cap 最后一轮再补 <goal-budget-reminder>。
常驻协议要求模型在本次 activation 结束前调用 goal_checkpoint 记录 「已完成 / 仍待办 / 下一步」，达成目标时调 goal_propose_completion。 最后一轮提醒仍是 turn cap 上唯一能在运行中拦截的机会：turn cap 在模型调用 之前检查，该轮 system prompt 末尾追加 <goal-budget-reminder>。 两者都只存在于该次请求的 system prompt 里、不进入会话历史 —— 预算是硬约束，提醒只是软引导。
Run 结束时的 outcome
不让 driver 从 Result<()> 或最后一段模型文字里猜结局。
progress_made no_progress needs_user completion_proposed budget_exhausted transient_error cancelled
无进展检测只看可观察变化（工具调用、Goal 事件），不看模型自述：只有文字的周期 记为 no_progress 并结束本次 Run，Goal 保持 running 等下一次 activation —— 它不会因此被暂停，也不会被误记成 progress_made。 单次失败或偶发网络错误记 transient_error，Goal 状态不变。 暂停、等待和 Run 结束都先落库，再通知 UI。
结束行说清两件事：Run 结束时 Runner 查一次本 Run 期间是否写过 checkpoint； 没写且 Goal 仍非终态，就在 🎯 … run finished: … 那行追加 (no checkpoint written)，并把同一事实写进 run_finished 事件 （note=no checkpoint written）。若 Goal 保持 running 且没有活动 Run，同一行再追加 — Goal idle; /goal resume to continue，不让日志与面板 各说各话。
完成提议 → 验证
Agent 认为目标已满足时提交完成提议及不可信的 criterion claims，Runner 先验证才进 verifying。claims 不写入 evidence —— 模型的完成文字、所有 Task 已完成、某个 turn 正常结束，统统不是成功判据。没有必需标准时这就是成功路径， 但完成记录必须标注 self-attested，并附上模型自述的检查（仍不是验收证据）。
验收账本（evidence）
人工验收写入确认者、时间与所针对的标准版本。
∅无必需标准 · 模型自述检查 → succeeded （self-attested）
✓全部必需标准 · 当前版本 evidence → succeeded
verifying → succeeded：有必需标准时，全部标准都要有当前版本的 evidence 才算成功； 自动验证尚未实现，当前由人工验收写入。用户修改目标或标准要提升版本号， 旧版本 evidence 不能默认沿用，必须按影响重新验证。
waiting_user → paused → cancelled / failed
等待用户与崩溃恢复：needs_user 落到 waiting_user； 人工验收不要求 Goal 恰好停在 waiting_user —— running （无活动 Run）与 paused 也能被 /goal accept 推进，只有 活动 Run 在途时拒绝。恢复的判据不能只看时间：lease 过期或持有进程已消失 （进程已退出，或 pid 被复用而 start-time 身份不匹配）就把 stranded running 落到 paused；identity 读不到或来自其他平台视为不可核验，退回纯时间过期语义， 绝不抢一个可能仍活着的持有者。Lease 在 Run 执行期间按 TTL/3 持续心跳， 收尾与释放只校验 owner + epoch（fencing），不再要求 lease 仍未过期。 运行期定时恢复刻意不落 idle running：那是本轮 no_progress 的合法落点，后台定时器不能把用户的任务按成暂停。
中断 vs 取消：运行中按 Esc 只中断当前 Run → paused （非终态，可 /goal resume）；只有 /goal cancel 写 cancel_requested 才落终态 cancelled —— 一次误触不会毁掉长任务。 预算耗尽时保存 checkpoint、用量和 stop reason 后进 paused。 已结束的 Goal 可 archive：它只把 Goal 移出面板，状态是结局、不能被改写 （failed 归档后仍报 failed），且归档是唯一被允许写终态 Goal 的操作。
